# 摄影协会网站 · 全面评估（2026-10-19）

> 评估对象：当前工程快照（Next.js 16 + Django/DRF）。
> 方法：读完全部文档与前端 15 个页面、后端 12 个模块、8 个容器配置；本地实跑接口核对排序与权限；对照 `DESIGN.md` 自述目标、`PRODUCT_REVIEW.md` 的用户反馈，以及 Emil Kowalski / Vercel Web Interface Guidelines / UI UX Pro Max 的检查项。
> 本文件只做判断，不含改动。文末列出待拍板事项。

## 一、结论先行

1. **工程完成度远超学生社团网站的平均水平**：审核状态机、对象级权限、私有文件网关、原片/展示图分离、并发名额锁、TOTP、审计、备份校验、28 项测试——这些不是"做给老师看的"，是能扛真实使用的底子。这部分不该推翻。
2. **但它目前是一个"关于摄影的网站"，不是一个"摄影协会的网站"**。把站名换成任何社团、把示例图换成任何图库，页面依然成立。这正是"无聊"和"模板感"的根源，不是配色或动效的问题。
3. **它回答了"怎么展示"，没有回答"为什么来、为什么留、为什么由这个协会来做"**。`PRODUCT_REVIEW.md` 已经点出这一点，但重做时最容易被"再加一点设计"掩盖过去。

## 二、功能实现盘点

### 2.1 已经真实贯通的部分

| 模块 | 实现程度 | 证据 |
| --- | --- | --- |
| 作品系列 + 照片排序 + 图注 | 完整 | `work-editor.tsx` 支持草稿、上传、改说明、调顺序、移除、撤回 |
| 审核流（草稿→待审→发布/退回→归档） | 完整且集中 | `services.transition()` 是唯一入口，API 与后台共用，页面无法绕过 |
| 活动报名 | 完整 | 事务 + 行锁 + 名额判断 + 重复报名 + 取消复用（`services.register`） |
| 归档资料 + 版本 + 授权下载 | 基本完整 | `DocumentVersion` + 每次下载重新鉴权 + 审计 |
| 私有文件网关 | 完整 | 原片不公开；展示图/缩略图按内容可见性鉴权；去除 EXIF |
| 成员档案与署名解耦 | 完整 | `Profile.user` 可为空，毕业后可撤权保留署名 |
| 多角色权限 | 完整 | 成员 / 编辑 / 活动负责人 / 资料管理员 / 超级管理员 |
| 管理后台 | Django 原生 | 复用同一状态机，禁止删除，只能归档 |

### 2.2 功能上的硬缺口

按"是否影响协会真实运转"排序，不按实现难度。

**P0-1 招新没有入口。**
全站唯一招新路径是「关于我们 → `#join` 一段文字 + 邮箱」。学生社团一年最重要的一次转化，现在要求新生写邮件。没有报名表、没有学院/年级/器材/作品链接字段、没有"提交成功"状态、没有后台待审列表。导航里连"加入"都没有。

**P0-2 活动照片无法汇总交付。**
这是 `PRODUCT_REVIEW.md` 里点名要验证的方向，也是所有摄影社团最高频的麻烦：活动结束后，参与者在群里刷图、互相问"原图发我"、最后靠网盘链接散落。当前实现是"每位成员各自建一个作品系列，手动关联活动"；活动页最多展示 6 组作品，**没有任何批量打包下载**。`api/files.py:69` 规定原片只有文件所有者或资料管理员能下载——普通参与者连自己出现在照片里的那张都拿不到。

**P0-3 作者发布之后收不到任何反馈。**
没有浏览量、没有收藏、没有"你的作品被选入本期"的通知；评论需要审核（合理），但**评论产生时不写 `Notice`**（`api/content.py:103-125`），作者永远不会知道有人在他的作品下说话。一个投稿系统如果不告诉作者"有人看了"，第二年就没人投稿。

**P1-1 已发布资料无法更新版本。**
`api/content.py:257` 要求草稿态才能加版本；`admin.py:56` 在已发布时直接隐藏版本内联。结果是：换届交接文档要改一版，必须"撤回→变草稿→公开页面消失→加版本→再提交→再审核"。资料库的日常动作被设计成了事故。

**P1-2 HEIC 不支持。**
`uploads.py:34` 只认 `.jpg/.jpeg/.png/.webp`，错误提示也只说这三种。iPhone 默认拍 HEIC，新生第一次投稿就会失败，还得自己转格式。这一条足以劝退一半人。

**P1-3 上传是串行的，且不能离开页面。**
`work-editor.tsx:104-116` 一次传一张，每张最多轮询 45×1.2s；前端不压缩。手机直出 48MP 照片常年超 25MB。传 20 张要十几分钟，中途刷新就断。

**P1-4 成员账号只能管理员逐个创建。**
没有邀请码、没有批量导入、没有"申请加入"。换届时要手工建十几个账号、勾工作人员、分配管理组——交接成本高。

**P1-5 搜索搜不到人、地点、图注。**
`api/content.py:55-59` 只搜 `title / description / tags`。摄影站的典型检索是"谁拍的""在哪拍的""那次银杏"。作者名和图注都不在索引里。

**P2 一组细节**
- 活动一旦报名，联系方式不能改，只能取消再报。
- 分页只有上一页/下一页，没有页码（`ui.tsx:119`）。
- 取消订阅式空状态：作品不足 4 条时首页错落网格会塌成单列（`page.tsx:77`）。
- 无效 UUID 打开详情走的是 error 边界"内容暂时没有打开"，而不是 404 页（`not-found.tsx` 写了但没用于数据 404）。
- `EventRow` 的"活动记录"把"未开放报名"和"已结束"混为一谈（`ui.tsx:81-99`）。
- 图片全部 `private, no-store`（`files.py:85`），返回列表再进来会重新下载一遍。

### 2.3 一个实测出来的逻辑错误

`models.py:140` 活动默认排序是 `-starts_at`（最新日期在前）。本地实跑 `/api/events/`：

```
2026-11-09  从曝光开始：摄影入门
2026-11-02  一起看照片：作品交流会
2026-10-26  周末走走：校园光影外拍
```

首页写的是"近期活动"，实际把**最远的那场**排在最前，最近的一场被挤到第三。对"报名"这个动作来说，排序是反的。活动列表同样把往期和未来混在一起，没有"即将开始 / 已结束"分组。

## 三、功能上的优点（值得保留的）

1. **状态机只有一份。** 页面、API、Django 后台都走 `services.transition()`，不存在"后台能改、前台不认"的分裂。这是很多外包项目都做不到的。
2. **权限是对象级的，不是菜单级的。** `permissions.visible_queryset()` 在查询层就过滤，不靠前端隐藏按钮；文件每次请求重新鉴权，撤回作品立刻生效。
3. **"公开档案"与"登录身份"分离。** 毕业生撤权后署名仍留在作品上——这个细节说明设计者真的想过协会的生命周期。
4. **失败有话说。** 图片处理失败有状态、有原因、可重试；报名满员/截止/重复都有具体文案，不用"操作失败"糊过去。
5. **示例内容被明确标记，且拒绝虚构。** 不编学校历史、人数、获奖、联系方式，甚至后台不许删除只许归档。这个克制很难得。
6. **会话与 CSRF 的处理是对的。** HttpOnly + SameSite、写操作校验 CSRF、登录限速、staff 强制 TOTP。

## 四、审美设计评估

### 4.1 做得好的地方

- **方向明确**：展墙白 `#f8f9f8` + 石墨 `#222b2e` + 深杉绿 `#244b43`，纸感、低饱和、无渐变无玻璃拟态。首页 1440px 截图里，"在日常里，看见。"与宽幅主图的关系是像展览入场，而不像 SaaS 落地页。
- **克制得对**：圆角只给控件，图片是自然矩形，没有阴影卡片墙、没有装饰编号、没有悬浮光球。这些正是 AI 生成页面的通病，它避开了。
- **几处真正的编辑级细节**：活动行用 Georgia 大号日期数字做版式锚点；归档行把"年份 / 类别 / 公开·内部"压成一行元信息；图片下方一定有图注；示例内容有 badge。这些是"内容即界面"的做法，比装饰高级。
- **移动端不是缩水版**：390px 下主图通栏出血、双列错落、导航折叠成图标、触控目标 44px，没有横向溢出。这块比多数同类站认真。
- **无障碍是真做了**：跳过导航、可见 focus、表单 label、`aria-live` 播报、原生 `<dialog>` 焦点管理、`prefers-reduced-motion` 全量降级、hover 效果限定 `pointer: fine`。

### 4.2 核心问题：它"精致但可预测"

"AI 模板感"不等于丑。这一版不丑。它的问题是：**每一屏都在重复同一个决定**。

首页四段结构完全一致：

```
12px 副标题（不同的视角，同样的热爱）
34px 宋体大标题（一些被留下的瞬间）
右侧箭头链接（全部作品 →）
下面一组条目
```

作品、活动、资料、招新横幅，四次重复。读者滑到第三屏就已经知道下一屏长什么样，于是"浏览"变成"确认"，没有信息增量，也没有惊喜。这正是"无聊"的机制。

### 4.3 逐项问题

**（1）文案抽掉了所有具体性。**
"在日常里，看见。""一些被留下的瞬间""一起，走出去""影像之外，经验也值得留下"——都是可以印在任何摄影 App 启动页上的句子。全站没有一个人名（除了"示例作者"）、没有一个真实地点、没有一次真实发生的事、没有一句成员说过的话。示例图 6 张全是 Unsplash 的风景与建筑，**没有一张人脸**。

摄影协会真正稀缺的不是"美图"，是"这群人在什么时候、去了哪、拍了什么、后来怎么样了"。现在的页面把最值钱的部分全部省略，只留下通用的抒情。

**（2）图片被当成色块用。**
- 首页主图固定 `height: clamp(320px, 41vw, 560px)` + `object-fit: cover`（`globals.css:240-254`），横幅比例由视口决定，与照片本身无关。竖幅人像在首页会被切头。
- 作品卡强制 `aspect-ratio: 4/3`，错落网格里第二张强制 `3/4`（`globals.css:311-324`）。**所有照片被裁成两种盒子**。对一个以"作品"为核心的站，这是最不该做的取舍：构图是摄影师的，裁剪权却被 CSS 拿走。
- 详情页反而保留原比例（`max-height: 85vh`），前后不一致。

**（3）头重脚轻。**
`88px` 标题占掉首屏近一半，主图只有 560px 高，而且只是"最近发布 + 勾了精选"的那一张——没有策展排序，没有手动指定。首屏最贵的位置交给了一个布尔字段。

**（4）字体落地不可控。**
`Songti SC / Noto Serif CJK SC / SimSun` 全部依赖本机字体，没有随站点分发（`DESIGN.md` 明确"不依赖外部字体网络请求"）。后果：Windows 上大字号宋体笔画细、灰度浅；iOS 用 Songti SC；Android 多数只有 Noto Sans CJK，宋体缺失会回落到别的 serif 甚至 sans。**同一页面在三种设备上是三种相貌**。再叠加 Georgia 数字 + 宋体标题 + 苹方正文，三种字体性格互相不认识。

**（5）辅文字号偏小，且有一处对比度不达标。**
`11px`（badge、页脚）、`10–12px`（手机端图注、活动状态）、`12–13px`（副标题）大量存在。同时 `--muted #66746f` 放在 `--soft #f0f2ef` 上实测约 **4.3:1**，低于 AA 的 4.5:1——`.info-panel`、`.empty-state`、`.member-card`、`.join-banner` 都用了这个组合。这是可量化、必须修的。

**（6）详情页与列表页气质断裂。**
列表是杂志式编排（左对齐、错落、图注在左）；点进作品后变成"居中大标题 + 居中图 + 居中图注 + 评论区"的默认博客结构。`DESIGN.md` 自己写的是"正文左对齐"，实现没遵守。整站的版式语言到这里就断了。

**（7）没有属于自己的视觉母题。**
除了那个默认的 Aperture 图标和"摄影协会"四个字，页面没有任何只属于这个协会的符号：没有 Logo、没有固定编号系统、没有统一的"拍摄地 / 时间 / 器材"签条、没有一条贯穿全站的网格线或栏距规则。所以把站名一换，它可以是任何社团的官网。**通用，是模板感的另一半。**

**（8）动效只有"按钮按下缩小 0.98"。**
克制是优点，但"展览"体验缺少因果：从列表进详情是整页硬跳转，图片没有入场，灯箱切换没有连续性，加载骨架是固定 300px 灰块，路由切换时页面会先塌一下。Emil 的原则不是"加动效"，而是"状态变化要有来处和去处"——现在没有。

**（9）前后台是两个世界。**
成员投稿在精心设计的前台；一旦要发活动、传资料、建账号、管标签，就跳进原生 Django admin：中英混排、字段密集、没有图片预览、没有批量操作、没有"发布前预览"。而协会 80% 的日常维护恰恰发生在后台。这是最大的体验断层，也是换届交接最难的部分。

## 五、为什么它"没有存在价值"——四条机制

1. **可替代性**：一个只展示美图的网站，替代品是小红书、朋友圈、Instagram、学校公众号。它没有提供任何这些渠道做不到的事。
2. **没有"正在发生"**：全站是完成时（被留下的瞬间、经验值得留下），没有现在进行时（这周谁在拍、下周去哪、这次活动还差 3 个人）。访客没有"下次再来"的理由。
3. **没有关系**：看不到谁是谁、谁带谁、谁和谁一起拍过。协会的核心资产是人和关系，页面把它们抽象成了"作者"字段。
4. **没有反馈回路**：作者发完就结束，访客看完就离开。没有计数、没有通知、没有下一站。

`PRODUCT_REVIEW.md` 问的"如果网站消失，会有哪件事变得困难"，目前答案是：**没有**。因为上面四件事它都没做。

## 六、如果重做：三条方向

不是"选一个风格"，是"选一个存在理由"。三条都可以做得很好看，区别在于谁愿意持续维护。

### 方向 A：当期展览（Issue）驱动

首页 = 本期一组展览：一位作者（或一个主题）+ 8–12 张照片 + 一段具体的故事 + 拍摄地/时间/器材 + 下一期预告。所有内容围绕"期"组织，作品、活动、资料都是某一期的附件。

- 优点：立刻摆脱模板感，有编辑权和策展感；每一期天然不同，首页不会重复自己。
- 代价：需要有人持续策展。一个月一期，人手不足就开天窗。
- 适合：有稳定的内容负责人（比如你本人）愿意每月花半天。

### 方向 B：活动照片交付工具（推荐作为内核）

以"一次活动"为原子：报名 → 拍摄 → 全员上传到同一场活动 → 参与者按"找自己 / 按作者 / 按时间"浏览 → 一键打包下载 / 生成微信分享卡。

- 优点：这是唯一高频、可验证、别人替代不了的事。做完这一件，"网站消失会变难"就有了答案。
- 代价：不"酷"，首页需要另外一套展示层；需要处理大文件、批量、下载带宽。
- 适合：活动多、参与人多、每次都被"发图"折磨的协会。

### 方向 C：校园影像档案

以时间与地点为轴，把"成大 / 成都"的影像按年份、地点、事件沉淀成可检索的档案，作品 = 档案条目。

- 优点：时间越久越值钱，是真正的长期资产；和"摄影协会"的身份强绑定。
- 代价：冷启动慢，需要采集标准（地点、时间、人物授权），两三年才看得出价值。
- 适合：有耐心、有归档习惯、想做长期项目的团队。

**我的判断**：**B 做内核，A 做门面。** 用 B 回答"为什么需要这个网站"，用 A 回答"第一次来为什么觉得好看"。C 作为 B 的自然沉淀（活动照片按年份自动变成档案），不需要单独做。

## 八、需要拍板的三件事

1. **定位选 A / B / C 哪条？** 或者告诉我"先不选，只修 P0"。定位不定，任何视觉改动都只是换一层皮。
2. **真实素材什么时候能给？** Logo、8–12 张有授权的人像/活动照、3 位成员的一句话、最近一次活动的日期地点人数、招新要求。**没有这些，再改版也还是"通用摄影模板"**——这一条比任何设计决策都重要。
3. **运维边界**：是否接受"一台 VPS + SQLite/Postgres + 对象存储"的极简部署？现有 8 容器方案（Caddy + Nginx + Next + Django + Celery + ClamAV + Postgres + Redis）在安全和隔离上更正确，但对每年换一届的学生团队，是长期负担。

拍板后我再动手。在此之前不改代码，避免把"待定方向的快照"改成"半新半旧的第四版"。
